# План восстановления административного доступа PostgreSQL

Статус: подготовлен и **выполнен 08.11.2026 после явного разрешения пользователя**. Обычный setup-database.ps1 пароль администратора не сбрасывает. Следующий текст сохраняет согласованный план и результат разовой операции; повторный сброс не требуется.

## Подтверждённая цель

- Служба `postgresql-x64-18`, состояние Running.
- Сервер `localhost:5432`, PostgreSQL 18 из `C:\Program Files\PostgreSQL\18\bin`.
- Каталог данных `C:\Program Files\PostgreSQL\18\data`.
- Файл аутентификации, подтверждённый postgres -C hba_file: `C:\Program Files\PostgreSQL\18\data\pg_hba.conf`.
- Целевая административная роль: `postgres`.

Пользователь сообщил, что пароль неизвестен, и прислал отказ аутентификации. До получения разрешения ни пароль, ни файл, ни состояние службы не менялись.

## Предлагаемая операция

1. Повторно проверить путь службы и контрольную сумму pg_hba.conf. При неожиданном изменении остановиться. Сделать точную резервную копию файла рядом с оригиналом, вне репозитория.
2. На время восстановления добавить перед существующими правилами ровно одно правило: `host postgres postgres 127.0.0.1/32 trust`. Оно разрешает локальное IPv4-подключение только к базе postgres от роли postgres без пароля. Другие роли, базы и внешние адреса под это правило не подходят. Пока правило действует, другие локальные процессы тоже смогут воспользоваться этим административным доступом.
3. Подключиться к 127.0.0.1:5432, проверить фактический каталог данных и сменить только пароль postgres на ранее выбранный пользователем. Секрет передаётся в памяти процесса, не сохраняется в файлы проекта, аргументы psql или журнал. Вывод SQL с паролем не публикуется.
4. В блоке finally восстановить исходные байты pg_hba.conf, включая исходную кодировку, и сверить SHA-256 с резервной копией. При неудаче смены пароля всё равно вернуть исходные правила; при неудаче восстановления сообщить об этом немедленно.
5. Новым соединением проверить вход с новым паролем после восстановления правил. Запустить подготовку только баз habit_tracker_sdd / habit_tracker_sdd_test и отдельной роли приложения. Затем выполнить интеграционные проверки основного сервера и зафиксировать результат.

На Windows изменения pg_hba.conf действуют для новых подключений сразу; перезапуск службы в этом плане не требуется. Это подтверждено [официальной документацией PostgreSQL 18](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html). Правило выбирается по первому совпадению в файле.

Операция меняет пароль административной роли общего сервера: другим клиентам, использующим postgres, потребуется новый пароль. Таблицы и существующие базы не удаляются. Старый неизвестный пароль после успешной смены восстановить без отдельного сохранённого секрета нельзя. Именно смена доступа к общему серверу требует отдельного разрешения, она не входит в обычное создание новой базы приложения.
